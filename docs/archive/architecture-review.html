Deepening Opportunities for flashwt

Surfacing architectural friction, eliminating shallow orchestration, and designing deep modules for maximum testability, locality, and AI-navigability.

Top Recommendation: Candidate 1 — Unified HydrationEngine

Hydration is the primary hot path of flashwt. Currently, flashwt-cli/src/hydrate.rs and commands/create.rs expose six fragmented procedural helpers (ingest, strategy selection, materialize, claim refs, snapshot refs, mirror publishing) that callers must manually choreograph. Consolidating this behind a deep HydrationEngine concentrates multi-threading, verification, atomic mirror persistence, and fallback ladders behind one cohesive seam.

Architectural Friction (Shallow Module)

hydrate.rs (800+ lines) presents a wide, shallow interface. Callers in create.rs and scratch.rs must manually manage a multi-step sequence:

  • ingest_dir() -> Ingested
  • select_strategy() & materialize()
  • claim_references() vs claim_snapshot_references()
  • publish_mirror()
  • store.flush() ledger update

Locality hazard: If a caller omits publish_mirror() or misplaces sidecar records, garbage collection mark-and-sweep correctness silently breaks.

Deepening Solution: HydrationEngine

Encapsulate all hydration lifecycle concerns behind a single deep interface: 

pub struct HydrationEngine<'a> {
    store: &'a mut DiskStore,
    config: &'a RunConfig,
}

impl<'a> HydrationEngine<'a> {
    pub fn hydrate(&mut self, req: HydrationRequest) -> Result<HydrationReport>;
}

Leverage & Locality: Callers provide the target paths and patterns. The engine handles directory scanning, snapshot vs per-file fallback, worker threading, blob verification, atomic mirror publishing, and ledger flushing.

CANDIDATE 02 Strong

Autonomous Store & Lease Reclamation Engine

crates/flashwt-store/src/gc.rs

Architectural Friction (Leaked Seam)

flashwt-cli/src/gc.rs::sweep_leases contains low-level store GC logic: directory size calculations, lease file parsing, process PID liveness probing, ledger parsing, refcount decrementing, and mirror removal, alongside shell git commands (git worktree remove --force, git branch -D).

Meanwhile, flashwt-store/src/gc.rs contains an independent mark-and-sweep for objects and snapshots. Storage durability invariants are scattered across CLI and store crates.

Deepening Solution: StoreReclaimer

Move lease lifecycle and store reclamation into a unified deep `StoreReclaimer` in flashwt-store, accepting an adapter for workspace cleanup: 

pub struct StoreReclaimer<'a, W: WorkspaceCleaner> {
    store: &'a mut DiskStore,
    cleaner: W,
}

impl<'a, W: WorkspaceCleaner> StoreReclaimer<'a, W> {
    pub fn sweep(&mut self, policy: SweepPolicy) -> Result<SweepSummary>;
}

Testability: The reclaimer can be tested with synthetic clocks, simulated dead processes, and mock workspace cleaners without spawning external git processes.

CANDIDATE 03 Worth exploring

Deep Snapshot Projection Module

crates/flashwt-cli/src/snapshots.rs
crates/flashwt-store/src/snapshot/mod.rs
crates/flashwt-store/src/snapindex.rs

Architectural Friction (Misplaced Logic)

flashwt-cli/src/snapshots.rs (717 lines) implements snapshot cache routing, v2 delta rebuild heuristics, selection ring rotation, sweep-race retry loops, and self-healing blob rebuilds (heal_blob).

These are foundational projection algorithms belonging to the storage layer, but they reside inside the CLI binary, making headless reuse impossible.

Deepening Solution: SnapshotProjectionEngine

Move projection planning, delta threshold heuristics, and healing retries into flashwt-store::SnapshotProjectionEngine. 

pub struct SnapshotProjectionEngine<'a> {
    store: &'a mut DiskStore,
}

impl<'a> SnapshotProjectionEngine<'a> {
    pub fn materialize_snapshot(&mut self, target: &Path, spec: SnapshotSpec) -> Result<ProjectionReceipt>;
}

Locality: Snapshot selection and delta diffing live directly next to snapshot metadata and WAL journals.

CANDIDATE 04 Worth exploring

Encapsulated Materialization & Capability Matrix

crates/flashwt-copy/src/materialize.rs
crates/flashwt-copy/src/selection.rs
crates/flashwt-cli/src/hydrate.rs

Architectural Friction (Leaked Physical Details)

Strategy negotiation (CoW clone vs Linux reflink vs copy_file_range vs byte-copy) is handled inside flashwt-cli/src/hydrate.rs::select_strategy.

Additionally, finalize_mode in flashwt-cli checks shares_inode_with_source and manually executes file removals and copies to avoid leaking chmod mutations to shared hardlinked blobs.

Deepening Solution: Deep Materializer

Consolidate filesystem capability detection, strategy selection, fallback chains, and mode normalization inside flashwt-copy::Materializer: 

pub struct Materializer {
    policy: StrategyPolicy,
}

impl Materializer {
    pub fn place_file(&self, src: &Path, dest: &Path, mode: u32) -> Result<PlacementReceipt>;
}

Locality: Callers request placement with a requested permission mode; flashwt-copy encapsulates all OS and filesystem edge cases.
